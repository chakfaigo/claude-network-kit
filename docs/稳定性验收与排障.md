# 稳定性验收与排障

稳定性需要同时满足：保护始终按预期、真实任务能完成、故障后能恢复、配置变化可追溯。不能只看Home绿色、一次测速或浏览器评分。当前版本没有改变3秒连接/5秒总时限、连续两轮恢复、固定出口与故障阻断规则；不声称根治供应商或链路故障。

## 先确认稳定的配置，再测稳定的体验

1. 锁定包版本、客户端版本、物理接口、当前路线与最终出口，确认没有另一网络工具自动接管。正常工作时不要反复切模式或重启核心。
2. 分别验证Claude保护、国内域名/IP直连、普通明确名单和未知目标；DNS另验。不要为了一个视频/语音或本地发现功能解除全局UDP/IPv6/PF限制。
3. 各客户端发新请求，用户决定登录时机后测试实际会用的小任务、长响应和上传。记录成功/失败、首字延迟、重试/断流、开始结束时间；不能用curl诊断代替真实业务。
4. 留下持续观察记录，覆盖实际工作时段，并记录观察时长、请求数、失败数、最长恢复时间和未解释异常。可以先做30–60分钟初测，再覆盖真实工作过程；这只是建议观察窗口，不是官方安全阈值或永久稳定保证。
5. 在维护窗口分别验证Origin、核心退出、供应商不可达、出口不符与恢复；再验客户端重开、唤醒、换Wi-Fi、重启及通知实际到达。没有安全实施条件的条目交维护者，保持待验收，不照搬历史停机脚本。

| 记录维度 | 必须区分 |
|---|---|
| 出口健康 | 是否返回预期固定IP；错误出口不能被另一个成功结果掩盖 |
| 探测质量 | 每个探测是否失败/超时；绿色可以包含单项超时 |
| 用户体验 | 真正任务的首字、断流、长响应/上传是否完成 |
| 恢复能力 | 何时阻断、何时恢复、是否重新验证；不能只看最终状态 |
| 配置稳定 | 自动更新、睡眠、换网及其他代理有无改写环境 |

两个健康探测目标属于同一服务商，不是两条完全独立的链路证明。状态变化重建核心会中断旧连接，短暂建连抖动可能放大为更长恢复时间；单次恢复全绿不能证明根因消失。

## 异常只按证据定位

先记录时间和模式，暂停新任务，保留本地诊断；依次检查本机入口、物理接口、代理网关、SOCKS连接、TLS、DNS、HTTP和认证/限额。未认证根路径返回403/404，不等于账号被封或网络失败。

对照直连家宽和前置家宽时，保持同一最终出口、可比任务与超时条件，并记录每次结果。前置只能改善到家宽的一段，不能保证修复住宅供应商故障；不要用一段更长诊断超时的成功冒充生产阈值已经通过。

如确需改变探测目标、阈值或恢复方式，单独形成设计：说明问题证据、改变的行为、错误出口阻断是否保持、失败路径测试、升级及回退。不能为减少红灯静默放宽；也不能把本版本阈值称为对所有线路都最优。

## 下一次不重复花时间

- 先跑只读接入检查，确定是配置缺项、旧版本还是实际线路问题。
- 不重新设置语言/时区，不清空账号，不安装未知“优化”脚本。
- 保留正确的分流、证书和固定出口；故障记录去掉凭据后再交维护者。
- 按[更新与维护](更新与维护.md)处理程序变更，成功后只复验受影响项，并保留仍适用的既有证据；关键故障路径变化必须补回归。
